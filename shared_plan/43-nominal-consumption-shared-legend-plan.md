# SharedPlan 43: 名目消費支出の期間共通凡例

## 背景

名目消費支出グラフでは、2018Q1より前にPlan40のCTI調整10費目と名目CTI補助系列を表示し、
2018Q1以降は従来の名目費目キーを使う。現在の `SpendingBarChart` は、2018年より前に
`keys` 全体を凡例へ出し、以降は補助系列を除いた `ctiKeys` を出すため、期間によって
凡例の項目・内部キー・順序が異なり得る。期間をまたいで同じ費目を比較・選択できるよう、
名目消費支出の費目凡例を全期間で共通化する。

## 目標と範囲

- 2005Q1以降の名目グラフで、同じ10費目を同じ順序・表示名・色で表示する。
- 2018Q1をまたいでも同一費目の表示／非表示状態を保つ。
- Plan40の2005Q1–2017Q4系列と2018Q1以降の既存系列の数値・出所・availability契約は変更しない。
- tooltip、データ表、CSV、CAGR、凡例トグルの公開データキーと行値の対応を壊さない。
- 実質消費支出の凡例や、他のチャートの凡例は対象外。

## 決定事項

- 名目費目の唯一の凡例registryを設け、10費目をこの順序で固定する: 食料、住居、光熱・水道、
  家具・家事用品、被服及び履物、保健医療、交通・通信、教育、教養娯楽、その他の消費支出。
- 各費目の論理的な凡例キーは既存の公開名目キー（例: `食料（名目）`）を正規キーとする。
  期間別データキーから正規キーへの解決はregistryの明示的なmappingで行い、ラベル文字列の
  部分一致や配列indexによる暗黙変換を使わない。
- 2005Q1–2017Q4のPlan40 v2キーと2018Q1以降の既存名目キーは、同じ費目へ一対一で対応させる。
  各時点に同じ費目の値が存在しない場合でも、凡例ボタンは消さず、series availabilityに従う。
- 全期間でlegend order、短縮表示名、色token、aria label、toggle対象をregistryから導出する。
  色は同じ費目に対して全期間で同一とし、既存の名目色との対応を保つ。
- 既存の `CTIミクロ四半期系列（名目）` は費目ではない合計補助系列として扱う。10費目の
  共通凡例へ混ぜず、表示を続ける場合は別枠の参考系列として明示し、費目toggle状態や費目順序を
  変えない。合計系列の表示／非表示をどこで操作するかは実装時に既存のユーザー操作との互換性を
  確認して決める。期間限定の系列を費目registryへ追加して共通性を崩さない。
- 期間境界はデータ選択・系列変換の責務とし、凡例表示を切り替える条件にはしない。
- 全選択解除は10費目の共通論理キーへ適用する。URLやReact stateに期間別内部キーを保存しない。

## テクニカルキーポイント

- 現行の期間条件は `src/app/components/SpendingBarChart.tsx` の
  `hasPreBoundarySupport` / `legendKeys = hasPreBoundarySupport ? keys : ctiKeys`。
  共通凡例化では、凡例項目の選択をdata row内のseries availabilityから切り離す。凡例が
  `keys` の期間別配列や、2005–2017用のサポート系列検出結果に依存しないこと。
- 公開データキーと投影は `src/lib/quarterlyPublicProjection.ts` が管理する。
  2018Q1より前の `CTI_ADJUSTED_V2_PUBLIC_KEY_BY_CATEGORY`（総合を除く10費目）と、
  2018Q1以降の `CONSUMPTION_NOMINAL_KEYS` を名目費目単位で対応づける。v1の残差キー、
  総合キー、内部分析キーを10費目mappingへ混入させない。
- 正規キーを表示／非表示stateとして使う場合、`normalizeSpendingChartData` または隣接する
  projection層で、各期間の内部キーを正規費目キーへ投影してからチャートへ渡す。チャート、
  tooltip、テーブル、CSVの公開列キーを変更する場合は全消費者を同時に追随させる。内部値の
  変換だけで済む場合も、公開されたCSV列名・既存のデータ契約が変わらないことを確認する。
- `src/lib/chartConstants.ts` の `getColorForNominalKey` / `getSpendingSeriesColor` と
  `DISPLAY_LABEL_OVERRIDES` は既存の色・ラベル契約である。Plan40側 `CTIミクロ調整系列（費目）`
  と既存側 `費目（名目）` が同一の10色と表示名へ収束するよう、色／ラベル解決を一つの
  registryに寄せ、キーごとのfallback色や表示名の揺れを避ける。
- `src/app/components/CpiChart.tsx` が構成する `nominalKeysWithSupport`、色配列、公開データ、
  データテーブル列、凡例stateを追跡する。色を配列indexだけに依存させない。系列順の変更が
  数値stack順や公開表の列順へ意図せず波及しないよう、legend orderとchart stack orderを
  明示的に区別する。
- 四半期の境界は2005–2017のPlan40 v2系列から2018Q1の既存費目別CTIへ一度だけ切り替える。
  2017Q4と2018Q1で同じ費目の二重描画、欠落、誤ったv1/v2キーのfallbackがないことを確認する。
- `status=invalid` / `seriesType=unavailable` / `value=null` の欠損行を0として描かない。
  欠損や部分的なmeasurementがあっても凡例項目は安定して残し、グラフ・tooltip・表・CSVで
  既存の空値と理由の表示契約を保つ。凡例共通化を理由に期間補間や0補完を導入しない。
- 名目費目のtoggle stateは両期間の対応する系列へ適用する。全選択解除、初期選択状態、
  実質凡例との既存連動、CAGR・CSVが参照する表示対象との関係を維持する。

## 境界と失敗時の扱い

2005Q1–2017Q4はPlan40 v2の費目系列を正規名目キーへ解決し、2018Q1以降は既存の費目別CTIを
同じ正規キーへ解決する。期間境界やregistry mappingを解決できないカテゴリは、似た名前から
推測せず、該当カテゴリを利用不能として機械可読な理由を維持する。10費目全体の順序を詰めて
並べ直したり、他費目の値・色・キーで穴を埋めたりしない。独立した合計補助系列は共通費目
registryの外に置く。

## 受入条件

- 2005Q1、2017Q4、2018Q1、および両側に値がある通常期間で、凡例が同じ10費目を同じ順序、
  表示名、色で表示する。
- 2017Q4から2018Q1をまたいでも同じ費目のtoggleが対応する系列を制御し、切替で凡例項目が
  増減しない。
- 全選択解除・再選択が10費目に対して一貫し、合計補助系列の状態が費目選択を誤って変えない。
- データ欠損・invalid measurementがあっても凡例の順序と項目は安定し、無効値を0として描かない。
- 2018境界で二重描画、欠落、誤ったv1/v2 mapping、stack合計の変化が発生しない。
- tooltip、データ表、CSV、CAGRとグラフが同じ論理費目・同じmeasurement値／状態を参照する。
- 実質側の凡例連動など既存挙動が維持される。

## テスト項目

- registryの10件、順序、正規キー、Plan40 v2キー／既存名目キー対応が一対一かつ重複なしである。
- pre-2018、post-2018、混在する境界データを使い、凡例項目・表示名・色・順序が同一である。
- 各カテゴリのtoggleと全選択解除を境界の前後で行い、対応する費目だけが隠れ、他費目・合計補助系列を
  誤って切り替えない。
- 2017Q4 / 2018Q1の同一カテゴリ対応、重複・欠落防止、stack order、色token parity。
- unavailable/nullのカテゴリ、部分的なavailability、全カテゴリ欠損でも凡例は安定し、数値0を生成しない。
- tooltip、データ表、CSV、CAGRの対象キーと値／状態が凡例の正規費目mappingと整合する。
- 既存の実質消費凡例連動および凡例色同期のテストを回帰確認する。

## 完了度の判定（実装後）

実装後の達成度は、以下のチェック項目の重みを合計して算出する。各項目は記載された証拠が確認でき、
その項目に関係する受入条件とテスト項目をすべて満たした場合に限り、重み全体を加算する。未完了、失敗、
未実施、または結果を確認できない項目は0%とし、部分点は付けない。100%は全項目が合格し、証拠が
揃った場合に限る。見積もりの進捗率や作業時間は、この完了度の代わりにしない。

## リスク

同一費目でも歴史系列と現行系列では内部キーや観測定義が異なるため、表示名を揃えるだけでは
toggle・tooltip・CSVの値が食い違う可能性がある。正規キーを公開データ全体へ導入する場合は既存の
利用者契約と型を調査し、必要な互換対応を追加する。合計補助系列の操作位置を変えると既存の利用者が
操作を見つけにくくなる可能性があるため、費目共通registryとは分けて実装前後で確認する。
