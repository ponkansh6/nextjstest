# happy-dom への E2E 契約移行プラン

## 目的

ブラウザ E2E で検証している内容を監査し、DOM 状態・純粋な計算・データ契約として
検証できるものを既存の Vitest + happy-dom に段階的に移す。実ブラウザが必要な
統合・レイアウト・入力デバイスの検証は維持し、重複する検証を減らす。

移行後もブラウザ E2E が担う統合保証を明示し、速度だけを理由に検出力を落とさない。
移行対象のフル Playwright E2E の所要時間は、同一条件での baseline / candidate 各1回の参考値として記録する。
この測定は統計的な改善判定を目的としない。

## 現状

- happy-dom は既存依存で、Vitest の既定環境として設定されている（`vitest.config.ts`）。
- コンポーネント検証には `tests/utils/logic-setup.tsx` があり、Recharts の描画を
  モックする既存パターンもある。
- Playwright E2E は 21 spec ファイルで構成される。
- 直近の変更後フルテストは **4分48.620秒**。Playwright は **122 pass / 19 skip**、
  約 **3分36秒**だった。比較対象の修正前実行は **5分11.600秒**。
- 移行前後の各1回は粗い所要時間の参考値に限り、ばらつきの区別や改善効果の判定には使わない。
  既存の値は引き続き履歴上の参考値とする。
- `measure:cache-e2e` はキャッシュ状態の影響調査用であり、フルスイートの
  ベンチマークとして代用しない。

## 移行テストの技術ポイント

### 検証環境の境界と実装上の注意

- happy-dom では、純粋な計算・入力から出力へのデータ契約、および Testing Library で
  描画したコンポーネントの DOM、role、accessible name、`aria-*` 属性、状態遷移を検証する。
  既定の Vitest 環境は `vitest.config.ts` の `happy-dom`、React コンポーネントの既存例は
  `tests/components/` にある。Recharts をモックする場合、そのテストの保証は mock に渡る
  props / DOM 契約までとし、実 SVG の生成保証を移したことにはしない。
- R4-4 の chart/table/CSV parity はこの移行で縮小・削除しない。純粋値や CSV serializer edge case は
  Vitest に追加・整理できるが、独立手書き fixture `tests/fixtures/chart-parity-independent.json` を
  使う実コンポーネント境界の統合検証と、全7対象について production Playwright で比較する全行・全列 parity
  は維持する。`hidden`、`adv=1`、名目/実質および GDP 境界 `2017Q4` / `2018Q1` も対象とする。
  fixture の期待値は app constants や DOM から生成しない。
- Playwright には、実ブラウザの layout / computed style / bounding box、SVG geometry、実際の
  scroll / viewport / hover・touch hit testing、native input の挙動、ダウンロード、Next route・
  Flight・hydration・server ready state の統合を残す。DOM 上に属性があることは、実際の
  keyboard focus、アクセシビリティツリー、スクリーンリーダーやブラウザの操作感を保証しない。
- 非同期更新は固定 sleep で待たず、最終 DOM を `findBy*` / `waitFor` 等で待つ。user-event を
  使う場合は `userEvent.setup()` を用い、操作を `await` する。fake timer を使うテストは
  timer を進める主体と React 更新の flush を明示し、実 timer と混在させない。callback が呼ばれ
  たことだけで終えず、再描画後の値・選択状態も確認する。
- happy-dom の `dispatchEvent` による event は browser の hit testing / native default action
  と同等ではない。click による状態遷移や明示的な callback は対象にできるが、pointer / touch
  座標、native select・keyboard、scroll と結び付く動作は実ブラウザに残す。ARIA は操作前後の
  `aria-expanded` / `aria-pressed` 等と role・名前の対応を確認し、属性の存在だけでなく状態と
  可視 DOM の整合を確認する。IntersectionObserver などを mock する場合も、通知後の mount 状態
  までを DOM テストの責務とし、実 scroll による通知は Playwright で維持する。

### assertion 対応のレビュー手順

付録 A はケース名から対象をたどる case/spec-level migration map とする。Phase 0 ではこれに加えて、
全 21 spec の実ソースにあるすべての `expect` / assertion を個別行に展開した assertion ledger を完成する。
ケース単位の一覧だけでは Phase 0 完了としない。ledger は各 assertion について少なくとも次を記録する。

| 必須欄                               | 内容                                                                                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Spec / case / assertion              | spec、case 名、assertion の一意な番号または識別子                                                                                        |
| Source                               | 実ソースファイルと行番号。expect / assertion の実際の条件式                                                                              |
| Execution condition                  | project、`test.skip` / `describe.skip` / 条件付き skip、loop 入力。生成される全ケースを展開し、skip の評価条件と現時点での実行可否を記録 |
| Observed contract / failure boundary | 観測する値・状態・描画・統合契約と、どの変化で失敗するか                                                                                 |
| Destination                          | Vitest の正確なファイル・test/assertion、または Playwright 維持先と維持理由。削除は代替 assertion への対応付けと削除理由                 |
| Review                               | 移行前レビュー担当、実装後レビュー担当、確認日またはレビュー記録参照                                                                     |

ledger の最小例:

| ID     | Spec / case                           | Source assertion                                                                      | Condition / expanded input                                                         | Contract / failure boundary                              | Destination or retained reason                                                  | Before / after reviewer                           |
| ------ | ------------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------- |
| CSV-01 | `chart-table-csv-parity` / CSV values | `tests/e2e/chart-table-csv-parity.e2e.spec.ts:NN`, `expect(actual).toEqual(expected)` | project=`chromium`; loop input=`対象名`（値ごとに個別行）; skip=`なし`をソース確認 | 行・列の値が一致しないと失敗。ファイル生成自体は含まない | Vitest の正確な test path を記入。production 全行全列 parity は Playwright 維持 | Phase 0 reviewer / implementation reviewer を記入 |

この例の `NN`、移行先、reviewer は記入形式を示すプレースホルダーであり、完了記録ではない。
ledger を作る際は loop の値を実際に列挙し、project ごとの実行条件と skip gate をソースで確認する。
Phase 0 のレビューでは、実装開始前に全行の対応・境界・条件を別 reviewer が照合する。実装後は、
実装者とは別の reviewer が Vitest の実 assertion、Playwright の残存 assertion、skip/project 条件、
fixture/mock の値を ledger と突合する。browser assertion を削除する場合はその直前に代替先と同一契約の
境界網羅をレビューし、削除後に全21 specの実行対象差分と ledger を再照合する。未解決 mismatch は
修正して再レビューするまで Phase 1 開始および関連 assertion の削除を止める。

移行作業中は ledger の各行をケース単位の台帳として、テスト編集ごとに次の対応をレビューする。

1. 移行前 assertion を意味単位に分解し、ケース名・ソース行・検証対象の値 / 状態 / 描画保証を
   ledger に記録する。setup、skip 条件、loop の全入力も対象範囲に含める。
2. 各 assertion に対して移行後の Vitest assertion、残す Playwright assertion、または削除理由を
   対応付ける。split では、移した論理 / DOM 契約と残る統合 / 描画契約を別項目にする。
   「同じユーザー操作をする」だけでは同じ assertion の代替と数えない。
3. 実装差分を読み、テスト名だけでなく実際に観測する値と失敗条件を比較する。fixture・mock が
   assertion を成立させるだけの値を固定していないか、追加したテストが本番経路と異なる条件を
   隠していないか確認する。
4. browser 側の削除は対応する Vitest assertion が存在し、同じ契約の境界値 / 遷移を覆うことを
   確認してから行う。browser 固有保証は残し、更新後の付録 A に双方の場所を記す。skip / project
   条件も照合し、Playwright の実行対象から誤って消えていないことを確認する。

### OpenSpec 同期の判定

テストの配置・mock・runner の変更のみで、利用者から見える振る舞い、データフロー、公開 API、
コンポーネント構成、要求されるアクセシビリティや性能契約に変更がなければ、プロダクト仕様の
変更とは判定しない。この場合は移行計画の付録 A と作業・検証記録を同期し、OpenSpec の
`Data Sources` / `Data Flow` / `Component Tree` / `Requirements` は変更しない。

移行中に上記のいずれかが変わる場合、または新しい外部契約・必須の非機能要件を導入する場合は
`openspec/specs/nextjstest/spec.md` の該当セクションを実装と同期し、変更要件には
`openspec/config.yaml` のルールどおり WHEN / THEN シナリオを記す。判定理由と対象仕様節を
作業記録に残し、単にテストが happy-dom に移ったことを仕様要件として追加しない。

## 計測プロトコル

### 目的と対象

計測対象は移行対象のフル Playwright E2E の経過時間だけとする。`package.json` の `test:e2e`
script は `playwright test` を実行するため、正式 command は `pnpm run test:e2e` とする。

`test:e2e:clean`、`test:e2e`）は品質受け入れとして維持するが、計測対象時間には含めない。

### 手順

1. baseline と candidate を各1回、同一 host、Node / pnpm version と環境条件で実行する。両 revision とも
   `pnpm run test:e2e` を使い、同じ選択規則でその commit 固有の全 E2E suite を実行する。対象範囲は

   `pnpm run build` を実行して作成する。install / build は計時せず、baseline / candidate の両方で同じ準備条件を適用する。
3. 対象 E2E process の開始直前を計測開始、process 終了を計測終了とし、経過秒数を記録する。
   他の品質ゲート、setup、cleanup の時間は含めない。
4. 実行ごとに次を記録し、raw output を保存する。完走しない場合は elapsed を完走時間として扱わず、
   status と中断・失敗の事実を残す。

| happy-dom が layout、SVG geometry、native scroll、touch、download、hydration を再現しない | それらをカバーする Playwright ケースを残し、DOM 移行後も browser smoke が対象経路を通るようにする               |

| cache や負荷が単回の時間値に影響する                                                      | 同一 host / runtime 条件で baseline / candidate を各1回測り、参考値として報告する。差を性能改善の判定に使わない |
| 移行により browser の網羅性が過度に落ちる                                                 | 品質受け入れゲートで既存 browser-only category と必要な inventory / functional parity を確認する                |

## 完了条件

- 移行した DOM / 計算 / データ契約が happy-dom または純粋な Vitest で検証される。
- viewport、WebKit、実 SVG geometry、hover 座標、download、Flight / hydration などの
  browser 固有契約が維持される。
- baseline / candidate の各 revision 固有の全 E2E suite を `pnpm run test:e2e` で1回ずつ実行し、elapsed time、process exit code、実行件数と実行条件を記録する。baseline は記録済みで、candidate は Phase 1 / 2 完了後に実施する。
- 依存準備は計時せず、E2E process 開始から終了までを計測する。
- baseline / candidate は同一の依存準備手順と runtime 条件で実行し、準備が完了してから E2E の計時を始める。
- elapsed time は粗い参考見積もりとしてのみ記述し、中央値・分散・統計的有意性・改善量を主張しない。
  完全性と browser 保証を速度と合わせて説明する。

### 付録 A の監査メモ

- `accessibility.e2e.spec.ts` の dark-mode / keyboard / animation describe はソース上 `describe.skip`。
  skip を実行済み保証とみなさず、現状維持として台帳に残した。focus management は実行対象。

  `tooltip-dismiss.e2e.spec.ts` の mobile group も同様に touch project gate を持つ。case 行に記録した。
- `range-change.e2e.spec.ts` の4つの bar-count case と scroll-retention case は条件成立時に
  runtime `test.skip()` へ入る可能性がある。行単位で skip を示した。

  body-level grouping した。series / chart loop がある場合も個々の test case 行はまとめていない。
- `section-tabs-scroll` の case 名は配列から生成されるため、3つの通常ケースと3つの lazy case を
  個別記載し、同じソース行をそれぞれリンクした。
