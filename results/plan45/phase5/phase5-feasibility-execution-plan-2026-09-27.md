# Plan 45 Phase 5 feasibility execution plan — 2026-09-27

## Review gate and scope

This artifact is a **plan only**. It proposes an evidence-led feasibility pass for (a) the six currently partial Phase 2 scenarios and (b) the 33 Phase 0 MAP-ineligible scenarios. No implementation, source assertion removal, or scenario-inventory change is authorized or claimed by this plan. Submit this plan for the initial JEV `plan_validity` review first. Begin Phase 5 execution only after a passing `valid_as_defined` review; a valid non-pass follows the single automatic clarification procedure, then requires a revised plan review before execution.

Phase 5 must distinguish three outcomes per exact source assertion and input condition:

1. **Browser Mode feasible:** the same contract and failure boundary can be tested by a component Browser Mode case, possibly with the current fixture boundary.
2. **Production-route Browser Mode feasible:** the same route/server/data boundary is reproducible through the existing custom production-route harness/provider, including configured viewport, engine, and real touch when required.
3. **Not established or not feasible:** current evidence does not yet support equivalent Browser Mode ownership, or a case-specific spike demonstrates a real provider/framework boundary. Keep Playwright ownership where it provides the required guarantee. Mark missing evidence or uncertain boundaries `unresolved`; do not relabel them impossible for convenience.

Viewport, layout, geometry, SVG measurement, scrolling, coordinate interaction, browser engine, or touch requirements alone are not impossibility findings. Every disposition needs exact source-callsite and predicate evidence. The 33 items are the historical MAP-ineligible cohort, not a conclusion that no future Browser Mode path exists.

## Evidence gates before any assertion removal

For every proposed Playwright reduction or removal, require all of the following in the row record:

1. Stable scenario ID ↔ immutable P42/source assertion ↔ exact input/project crosswalk.
2. Browser Mode destination demonstrates the same failure boundary and predicate at equal or stronger thresholds; production dependencies use the built production route/data path.
3. Required browser engine, mobile device context, touch/scroll/coordinate inputs and skip/project range are covered.
4. Browser Mode result and relevant consolidated E2E result pass; any failure/retry is preserved as instability evidence, not hidden.
5. Existing unit/component overlap and retained route/URL/server/data/download integration are explicitly reviewed.
6. Independent reviewer approves the exact removed/reduced assertions and remaining Playwright responsibilities.
7. Updated inventory/ledger records disposition, E, whole-scenario M, rationale, and evidence links.

Until all gates pass for an assertion, keep its Playwright owner. If a capability probe is negative, record the exact attempted configuration, provider/Next error, and why the exact assertion cannot be preserved; a visual/layout/touch label alone is not evidence. If results are ambiguous or lack same-boundary evidence, leave the case `unresolved` and retain Playwright.
