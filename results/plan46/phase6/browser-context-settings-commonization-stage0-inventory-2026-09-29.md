## 共通helper境界の判断

**context-only helperを採用する。** Inventoryでは全callsiteが`context.newPage()`を別呼び出しとして持ち、その後のpage処理はcommand内にある。一見同じ形だが、scenarioごとのpage設定・page操作、route結果の収集、failure判定、provider差が異なる。pageをhelperが作って渡す形にすると、page所有とエラー境界をhelperへ移し、route固有の責務まで抽象化するため、今回の計画の責任境界に合わない。

候補APIは`withIsolatedContext(browser, options, callback)`。helperの責務は受け取ったBrowserから独立contextを1つ生成し、callback後にそのcontextを閉じることに限定する。page生成、Browser取得、provider判定、route navigation/wait/assertion、scenario入出力、skip/failure判断はcommand側に残す。context作成後のcallback/page作成失敗を含めてcloseするfinallyと、callback errorがclose errorを隠されないfailure contractを実装時にテストする。

## 型・依存バージョン・公式資料

- route commandは`BrowserCommand`を`vitest/node`からtype importする。Vitest 4.1.11の`BrowserCommandContext`自体にはPlaywrightの`context`がないが、`@vitest/browser-playwright` 4.1.11の`dist/index.d.ts`が`declare module "vitest/node"`で`page`と`context: BrowserContext`を追加している。
- 各commandは`context.browser()`を使う。これはPlaywright `BrowserContext.browser()`で、戻り値の型は`Browser | null`。null guard後の型はPlaywright `Browser`。
- helperでは`Browser`と`BrowserContextOptions`を`@playwright/test`の公開entrypointからtype-only importできる。`@playwright/test` 1.62.1 / Playwright 1.62.1をlockfileとinstalled package metadataで確認した。
- Vitest `BrowserCommand`型は`(context, ...args)`のcustom command契約。Playwright APIでは`Browser.newContext(options?)`がcontextを生成し、`BrowserContext.newPage()`は別操作。これはpage付きhelperを必須にしない根拠でもある。
- Vitest 4.1.11、`@vitest/browser-playwright` 4.1.11、Playwright 1.62.1。

公式資料:

- [Playwright Browser API (`browser.newContext`)](https://playwright.dev/docs/api/class-browser)
- [Playwright BrowserContext API (`context.newPage`, `context.close`, `browser`)](https://playwright.dev/docs/api/class-browsercontext)
- [Vitest Browser Mode guide](https://vitest.dev/guide/browser/)
- [Vitest Browser Mode custom commands](https://vitest.dev/api/browser/commands)

Playwright Browser docsは`browser.newContext()`で隔離されたcontextを作るAPIを定義し、BrowserContext docsはcontextを明示的にcloseすることを推奨している。これらはlifecycle helperのAPI根拠であり、runtime短縮の根拠ではない。

### Built route smoke runner

`test:browser:next-route-poc:built`というpackage scriptは`node scripts/run-next-route-poc.mjs`を呼ぶ。script名に反して単独の`next-route-poc` testだけを選ばず、引数なしでは`vitest.browser.aggregate-chromium.config.ts`と`vitest.browser.webkit.config.ts`の両方を実行する。built runnerは`.next/BUILD_ID`をチェックし、無ければ`pnpm run build`を先に要求する。production serverとbrowser API portを管理し、`--only=phase6-b01`〜`--only=phase6-b14`でphase configを個別選択できる。profile JSONは任意の`--profile-json`で生成する。したがって focused routeの確実な前提はbuilt artifactであり、test本体/全suiteの計測はこのStage 0では行っていない。
