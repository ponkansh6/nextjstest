# バグ修正 TDD ワークフロー

## 目的

バグ報告を受けてから修正完了までを、以下の固定9ステップで進める。ステップの省略・並び替えは禁止する。特に「テストを書かずに直接ソースコードを直す」「赤を確認せず修正してから初めてテストを書く」は、このワークフローの目的(テストが実際にバグを検知できることを証明すること)を無効化するため禁止する。

この順序は本リポジトリで実際に機能した実績を持つ。消費支出グラフの四半期(Q1〜Q4)絞り込みが効かないバグ(コミット `26d956b`)は、この9ステップを踏んだことで、既存テストの薄さ(コールバックが呼ばれたことしか見ていない)まで含めて修正できた。作業前に `git show 26d956b` でこの実例を確認することを推奨する。

## 前提コマンド(このプロジェクト固有)

| 目的                                                   | コマンド                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------ |
| ユニット/コンポーネントテスト(vitest、数秒で完了)      | `pnpm run test:all`                                          |
| E2E用ビルド(**E2E実行前に必須**)                       | `pnpm run build`                                             |
| E2Eテスト全体(chromium / chromium-dark / mobile-pixel) | `pnpm run test:e2e`                                          |
| E2Eの一部だけ高速に再実行                              | `npx playwright test --project=chromium -g "テスト名の一部"` |
| 残存 next-server プロセスの確認                        | `ps aux \| grep next-server`                                 |
| 残存プロセスの停止                                     | `kill <PID>`(または `pkill -f "next start"`)                 |

`playwright.config.ts` の `webServer.reuseExistingServer` は `false` 固定である。これは、ポート3000に古い `next-server` が残っていると、ビルドID/アセット不整合で無関係なテストまで大量に落ちる事故が実際に起きたための設定である。したがって E2E を実行する前に必ず次の2点を満たす:

1. 検証対象のコード変更後に `pnpm run build` を明示的に実行済みであること(`.next` が古いまま `next start` を起動すると、変更が反映されないまま検証したことになる)
2. `ps aux | grep next-server` で古いプロセスが残っていないこと(残っていれば kill してから実行する)

## ステップ1: バグ内容確認

**確認内容**: ユーザー報告を再現条件(操作手順・期待結果・実際の結果)に分解する。関連するコンポーネント/関数を `grep` や `Read` で特定し、疑わしい実装箇所に当たりをつける。

**コマンド例**:

```bash
grep -rn "<関連キーワード>" src/ server/
```

**次へ進む条件**: 「何をすれば」「何が起きるべきで」「実際は何が起きるか」を1〜2文で説明できる状態になったら次へ進む。

## ステップ2: テスト内容確認

**確認内容**: バグが疑われる箇所に関する既存テスト(ユニット/コンポーネント/E2E)を洗い出し、それらが実際に何を検証しているかを読む。「テストがある」ことと「テストがバグを検知できる」ことは別である点に注意する。

以下の薄いテストのパターンに該当しないか確認する:

| パターン                                     | 症状                                                                                                              |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| (a) コールバックだけ検証                     | コンポーネントテストが `onToggle` 等のモック呼び出しだけを確認し、呼び出し先の実データ変化を見ていない            |
| (b) 純粋関数だけ検証                         | `computeChartData` 等の単体テストは関数自体の正しさしか証明せず、本番コードがその関数を実際に呼んでいる保証がない |
| (c) クラッシュしないことだけ確認する薄い E2E | 「エラーが出ない」ことしか assert していない smoke test                                                           |

**コマンド例**:

```bash
grep -rln "<関連コンポーネント名>" tests/
```

**次へ進む条件**: 関連テストの一覧と、それぞれが実際に何を assert しているか(上記パターンに該当するかどうか含め)を把握したら次へ進む。

## ステップ3: バグをカバーするテスト作成

**確認内容**: ステップ1の再現条件を、実データの変化を assert するテストとして書く。単体テストで再現できるならそちらを優先するが、UI操作起因のバグ(クリック→実際の描画結果が変わらない、等)は E2E でしか再現できないことが多い。その場合 `tests/e2e/` に新規ファイルを追加、または既存ファイルに追記する。

assert 対象は「コールバックが呼ばれたか」ではなく「実際に見える結果(DOM上の要素数、表示テキスト、計算結果の値など)が変化したか」にする。

**コマンド例(E2Eテンプレートとして `tests/e2e/spending-filter.e2e.spec.ts` を参照)**:

```bash
sed -n '1,40p' tests/e2e/spending-filter.e2e.spec.ts
```

**次へ進む条件**: 新規/追記したテストが「バグが直っていれば pass、直っていなければ fail する」ロジックになっていることを自分で説明できたら次へ進む(この時点ではまだ実行しない)。

## ステップ4: テストがカバーできていなかった原因検証

**確認内容**: ステップ2で洗い出した既存テストが「なぜこのバグを検知できなかったのか」を具体的に特定する。ステップ2の(a)(b)(c)のどれに該当するかを明言する。単に「テストが足りなかった」で終わらせず、どのテストの、どの assert が、何を見落としていたのかまで掘り下げる。

**次へ進む条件**: 「既存の◯◯テストは△△だけを見ており、□□を見ていなかったため検知できなかった」という一文を書けたら次へ進む。

## ステップ5: バグ以外にテストでカバーできていない部分の有無を確認

**確認内容**: ステップ4で特定した見落としパターン(a/b/c)が、同じコンポーネント/モジュールの他の機能にも当てはまらないか横展開して確認する。例えば「Q1〜Q4トグルのテストが薄かった」なら、「費目トグルのテストも同じパターンで薄くないか」を確認する。

**コマンド例**:

```bash
grep -n "onToggle\|onToggleQuarter" tests/components/*.test.tsx
```

**次へ進む条件**: 他に同様のカバレッジ不足があるかないかを明確に判定(Yes/No)したら次へ進む。

## ステップ6: (カバーできていない部分があれば)その部分のテスト作成

**確認内容**: ステップ5でYesだった場合のみ実施する。既存の薄いテストを、モック呼び出し確認から実データ変化の確認へ書き換える、または新規テストを追加する。ステップ5でNoだった場合はこのステップをスキップし、その旨を明記してステップ7に進む。

**次へ進む条件**: 追加/強化したテストが実データの変化を assert するようになったら(またはステップ5がNoで明示的にスキップしたら)次へ進む。

## ステップ7: テスト実行してバグ部分の赤を確認

**確認内容**: ステップ3・6で作成/強化したテストを実際に実行し、FAIL の出力を目視で確認する。**コードを読んだだけの推測で「これは失敗するはずだ」と済ませることは禁止**。ユニットテストで再現するものは `pnpm run test:all`、E2Eでしか再現しないものは以下の手順で実行する。

**コマンド例(E2E)**:

```bash
ps aux | grep next-server   # 残存プロセスがあれば kill
pnpm run build               # 変更を確実に .next に反映
npx playwright test --project=chromium -g "<新規テスト名の一部>"
```

**コマンド例(ユニット/コンポーネント)**:

```bash
pnpm run test:all
```

**次へ進む条件**: 対象テストが実際に FAIL(赤)した出力を確認できたら次へ進む。PASS してしまった場合はテストの assert が弱い可能性が高いため、ステップ3/6に戻って強化する。

## ステップ8: ソースコード修整

**確認内容**: ステップ7で確認した赤を最小限の変更で解消する。ステップ1〜4で特定した根本原因(例: 特定の state が計算に反映されていない)を直接修正し、副作用的な回避策(テストだけを通す修正)にしない。

**次へ進む条件**: 修正差分を `git diff` で確認し、根本原因に対応する変更になっていることを説明できたら次へ進む。

## ステップ9: テスト実行してバグ部分の緑を確認

**確認内容**: ステップ7と**同一のテスト実行コマンド**を再実行し、PASS(緑)を確認する。同一コマンドで再実行することで、赤→緑が同じテストに対する真のBefore/Afterであることを保証する。E2Eの場合はステップ8の変更を反映させるため、再度 `pnpm run build` してから実行する。

**コマンド例**:

```bash
ps aux | grep next-server   # 残存プロセスがあれば kill
pnpm run build
npx playwright test --project=chromium -g "<ステップ7と同じテスト名>"
```

緑を確認したら、必要に応じて広い範囲の回帰も確認する:

```bash
pnpm run test:all
pnpm run test:e2e
```

**完了条件**: 対象テストが緑になり、かつ全体テスト(`test:all` / `test:e2e`)も通過したら修正完了とする。コミットする場合はコミットメッセージを日本語で書き、`--no-verify` や hooks バイパスは使用しない(`AGENTS.md` により禁止・ブロックされている)。
