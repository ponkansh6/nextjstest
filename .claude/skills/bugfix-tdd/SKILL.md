# バグ修正 TDD ワークフロー

## 目的

バグ報告を受けてから修正完了までを、以下の固定9ステップで進める。ステップの省略・並び替えは禁止する。特に「テストを書かずに直接ソースコードを直す」「赤を確認せず修正してから初めてテストを書く」は、このワークフローの目的(テストが実際にバグを検知できることを証明すること)を無効化するため禁止する。

> **注意**: このスキルは汎用テンプレートです。`## 環境別コマンド設定` セクションのコマンドを、使用するプロジェクトの実コマンドに置換してから使用してください。

## 環境別コマンド設定（プロジェクトごとに置換必須）

このスキルで実行するテストコマンドはプロジェクト環境に依存する。作業を始める前に、以下をプロジェクトの実コマンドに置換してから使用すること。

| 目的                                  | プレースホルダ              |
| ------------------------------------- | --------------------------- |
| ユニット/コンポーネントテスト（高速） | `<unit-test-command>`       |
| E2E用ビルド（E2E実行前に必須）        | `<build-command>`           |
| E2Eテスト全体                         | `<e2e-test-command>`        |
| E2Eの一部だけ高速に再実行             | `<e2e-single-test-command>` |
| 残存サーバープロセスの確認            | `<ps-command>`              |
| 残存プロセスの停止                    | `<kill-command>`            |

E2E環境では、ビルド成果物が古いままサーバーが起動すると変更が反映されない。検証対象のコード変更後にビルドを明示的に実行し、古いサーバープロセスが残っていないことを確認してからE2Eを実行すること。

## ステップ1: バグ内容確認

**確認内容**: ユーザー報告を再現条件(操作手順・期待結果・実際の結果)に分解する。関連するコンポーネント/関数を `grep` や `Read` で特定し、疑わしい実装箇所に当たりをつける。

**コマンド例**:

```bash
grep -rn "<関連キーワード>" src/ server/
```

**次へ進む条件**: 「何をすれば」「何が起きるべきで」「実際は何が起きるか」を1〜2文で説明できる状態になったら次へ進む。

## ステップ2: テスト内容確認

**確認内容**: バグが疑われる箇所に関する既存テスト(ユニット/コンポーネント/E2E)を洗い出し、それらが実際に何を検証しているかを読む。「テストがある」ことと「テストがバグを検知できる」ことは別である点に注意する。

以下の薄いテストのパターンに該当しないか確認する:

| パターン                                     | 症状                                                                                                         |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| (a) コールバックだけ検証                     | コンポーネントテストが特定のコールバック等のモック呼び出しだけを確認し、呼び出し先の実データ変化を見ていない |
| (b) 純粋関数だけ検証                         | 内部の単体テストは関数自体の正しさしか証明せず、本番コードがその関数を実際に呼んでいる保証がない             |
| (c) クラッシュしないことだけ確認する薄い E2E | 「エラーが出ない」ことしか assert していない smoke test                                                      |

**コマンド例**:

```bash
grep -rln "<関連コンポーネント名>" tests/
```

**次へ進む条件**: 関連テストの一覧と、それぞれが実際に何を assert しているか(上記パターンに該当するかどうか含め)を把握したら次へ進む。

## ステップ3: バグをカバーするテスト作成

**確認内容**: ステップ1の再現条件を、実データの変化を assert するテストとして書く。単体テストで再現できるならそちらを優先するが、UI操作起因のバグ(クリック→実際の描画結果が変わらない、等)は E2E でしか再現できないことが多い。その場合テストディレクトリに新規ファイルを追加、または既存ファイルに追記する。

assert 対象は「コールバックが呼ばれたか」ではなく「実際に見える結果(DOM上の要素数、表示テキスト、計算結果の値など)が変化したか」にする。

**コマンド例**:

```bash
# プロジェクトの既存テストを参考に再現テストを作成する
```

**次へ進む条件**: 新規/追記したテストが「バグが直っていれば pass、直っていなければ fail する」ロジックになっていることを自分で説明できたら次へ進む(この時点ではまだ実行しない)。

## ステップ4: テストがカバーできていなかった原因検証

**確認内容**: ステップ2で洗い出した既存テストが「なぜこのバグを検知できなかったのか」を具体的に特定する。ステップ2の(a)(b)(c)のどれに該当するかを明言する。単に「テストが足りなかった」で終わらせず、どのテストの、どの assert が、何を見落としていたのかまで掘り下げる。

分析結果は**検知ギャップ一覧**として列挙する。各行は「既存の◯◯テストは△△だけを見ており、□□を見ていなかった(パターンX)」+「それを閉じるテストの種類(ユニット/コンポーネント/E2E)」を併記する。

**次へ進む条件**: 検知ギャップ一覧を1ギャップ=1行で書き、各ギャップに「閉じるテストの種類」まで併記できたら次へ進む。

## ステップ5: バグ以外にテストでカバーできていない部分の有無を確認

**確認内容**: ステップ4で特定した見落としパターン(a/b/c)が、同じコンポーネント/モジュールの他の機能にも当てはまらないか横展開して確認する。例えば「あるトグルのテストが薄かった」なら、「他のトグルのテストも同じパターンで薄くないか」を確認する。

**次へ進む条件**: 他に同様のカバレッジ不足があるかないかを明確に判定(Yes/No)したら次へ進む。

## ステップ6: (カバーできていない部分があれば)その部分のテスト作成

**確認内容**: **ステップ4の検知ギャップ一覧の全ギャップ**と、ステップ5で見つけた横展開のカバレッジ不足を、対応するテストで閉じる。既存の薄いテストを、モック呼び出し確認から実データ変化の確認へ書き換える、または新規テストを追加する。

- ステップ3の再現テストが既にギャップを閉じている場合は、そのギャップに「再現テストで閉じた」と明記してスキップできる。
- ステップ4のギャップとステップ5の不足が両方無い場合のみこのステップをスキップし、その旨を明記してステップ7に進む。

**次へ進む条件**: 検知ギャップ一覧の各行が「対応テストで閉じた」または「再現テストで閉じた」と明記され、ステップ5の不足にも対応済みであることを確認できたら次へ進む。

**E2E回帰テストのスコープ**: 追加・強化するE2Eテストは、同一描画(ページロード)内で対象コンポーネントの**全系列・全項目をループ検証**すること。既存テストのサンプル検証パターン(代表値のみ)に無批判に倣って絞らない。ページ描画後にアサーションを追加する実コストはほぼゼロであり、全項目検証のほうが回帰ガードとして堅牢。検証対象の対応表(カテゴリ→系列→ラベル等)は本番コードから導出し、テスト側で写経しない。

## ステップ7: テスト実行してバグ部分の赤を確認

**確認内容**: ステップ3・6で作成/強化したテストを実際に実行し、FAIL の出力を目視で確認する。**コードを読んだだけの推測で「これは失敗するはずだ」と済ませることは禁止**。ユニットテストで再現するものは `<unit-test-command>`、E2Eでしか再現しないものは以下の手順で実行する。

**コマンド例(E2E)**:

```bash
<ps-command>   # 残存プロセスがあれば kill
<build-command>              # 変更を確実にビルド成果物に反映
<e2e-single-test-command>
```

**コマンド例(ユニット/コンポーネント)**:

```bash
<unit-test-command>
```

**次へ進む条件**: 対象テストが実際に FAIL(赤)した出力を確認できたら次へ進む。PASS してしまった場合はテストの assert が弱い可能性が高いため、ステップ3/6に戻って強化する。

## ステップ8: ソースコード修整

**確認内容**: ステップ7で確認した赤を最小限の変更で解消する。ステップ1〜4で特定した根本原因(例: 特定の state が計算に反映されていない)を直接修正し、副作用的な回避策(テストだけを通す修正)にしない。

**次へ進む条件**: 修正差分を確認し、根本原因に対応する変更になっていることを説明できたら次へ進む。

## ステップ9: テスト実行してバグ部分の緑を確認

**確認内容**: ステップ7と**同一のテスト実行コマンド**を再実行し、PASS(緑)を確認する。同一コマンドで再実行することで、赤→緑が同じテストに対する真のBefore/Afterであることを保証する。E2Eの場合はステップ8の変更を反映させるため、再度 `<build-command>` してから実行する。

**コマンド例**:

```bash
<ps-command>   # 残存プロセスがあれば kill
<build-command>
<e2e-single-test-command>
```

緑を確認したら、必要に応じて広い範囲の回帰も確認する:

```bash
<unit-test-command>
<e2e-test-command>
```

**完了条件**: 対象テストが緑になり、かつ全体テストも通過したら修正完了とする。**さらに、ステップ4の検知ギャップ一覧が「対応テストで閉じた」「再現テストで閉じた」のどちらかで全行埋まっていることを確認する**(分析だけしてテストを書いていないギャップが残っていないこと)。コミット時はプロジェクトのコミット規約・フック規約に従うこと。
