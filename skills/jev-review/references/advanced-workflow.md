# Advanced local workflow and compatibility

This file documents behavior implemented by `scripts/jev-request.mjs`. These schemas, verdict rules, and CLI modes are local workflow behavior; they are not JEV API operations or API-native fields. Every clarification/follow-up judgment is a separate `POST /v1/systemone` request.

## New initial-review interpretation

- New standard requests use `schemaVersion: "jev-review-initial-distribution-v3"`, with one choice question containing exactly `valid_as_defined`, `requirements_mismatch`, `missing_prerequisites_info`, `incomplete_implementation_info`, `implementation_issue`, `scope_violation`, `other`, and `indeterminate`.
- Only `valid_as_defined` passes. The six reason choices are non-pass diagnoses, not severity levels; do not infer `valid_but_limited` or `not_valid` from them. `indeterminate` means unresolved context. Preserve the selected confidence and complete probability distribution; `passProbability` is the mass assigned to `valid_as_defined`.
- A complete reason diagnosis includes a case-specific finding, affected location or requirement, observed evidence, and either a concrete proposed fix or exact additional evidence. Never use a category name as the finding or invent details from criteria. Incomplete details remain non-pass with `diagnosisStatus: "incomplete"` and `followUpRecommended: true`. `indeterminate` is incomplete. Unknown, missing, duplicated, or malformed answers fail closed.

## One automatic clarification

After a normally validated v3 initial answer with any non-pass choice, the client derives at least two mutually exclusive, case-specific immediate actions from the finding, affected requirement, evidence, proposed fix, and needed evidence, then submits exactly one more JEV request. The usual choices separate: change only the implementation under the current requirement; revise only the requirement under the current implementation; or collect evidence without changing either. Each option repeats the same finding, affected location or requirement, and observed evidence (or explicitly says JEV omitted it), and excludes the other actions. Codex does not select an option or ask the user to choose.

The clarification asks JEV to select a choice ID and return a case-specific finding, affected location or requirement, observed evidence or exact `neededEvidence`, concrete `nextAction` or `proposedFix`, and `remainingUncertainty` (`none` when resolved). Tie the details to the selected action. Preserve the initial result unchanged, including its `decisionSummary`, probabilities, and raw response. Store clarification separately with `effectiveVerdict: "requires_revalidation"`; it can never promote the initial result.

Only a clarification with all required diagnosis details is complete. A choice-only or otherwise incomplete answer retains `selectedChoice` and `rawResponse`, and is stored with `resolution: "unresolved"`, `diagnosisStatus: "incomplete"`, and `unresolvedReasons`. Transport failure, invalid response, unsupported format, or a choice outside the offered set is also preserved as unresolved beside the initial result. Do not chain another clarification or ask the user to repair it. Apply the selected bounded action or collect evidence, run relevant checks, and submit a new normal initial review. Initial API/response failures, unsupported formats, or unknown/missing initial choices retain initial-error behavior and do not trigger clarification. A passing initial answer does not trigger it.

## Saved-result and CLI compatibility

- Results using `jev-review-initial-distribution-v2` remain readable with their original choices (`evidence_insufficient`, `acceptance_gap`, `implementation_mismatch`, `constraint_conflict`) and summary semantics. Do not use those IDs for new requests.
- Prior three-question results (`failure_reason`, `next_action`, and one main question) and legacy one-question results remain readable with their original semantics. In the three-question format, only the main choice determines verdict; diagnostic inconsistencies fail closed as defined by that schema. Legacy custom non-empty criteria remain accepted; only exact `valid_as_defined` can pass.
- New local results retain `reviewSchemaVersion` and the original request metadata. Parse and clarify according to that version while retaining old saved results. The existing generic `--follow-up` utility remains non-standard; its fixed reason IDs are `requirements_mismatch`, `missing_prerequisites_info`, `incomplete_implementation_info`, `implementation_issue`, `scope_violation`, and `other`. Explicit `--reasons-file` remains supported.
- Explicit `--clarify INITIAL_RESULT --choices-file FILE --choice ID` remains supported. A choices file has `version: 1`, a question, `selectionMode` (`single` or `multiple`), and at least two choices with unique `id`, `label`, and `description`. Repeated `--choice` is valid only in multiple mode. Clarification requires explicit valid choice IDs and always sets `effectiveVerdict: "requires_revalidation"`. Manual clarification and generic follow-up are compatibility utilities, not part of the standard automatic path.
- For old saved v3 diagnosis summaries, preserve `decisionSummary` fields (`choice`, `confidence`, full `probabilities`, and returned finding/evidence/remedy details). A follow-up can explain or refine a diagnosis but cannot change the initial verdict; only a new regular review after evidence or a fix can pass.

## Authentication and data handling

The client prefers explicitly exported `TYPESAFE_API_KEY`; otherwise it reads `TYPESAFE_API_KEY` from `.env.local` in ancestor directories of the current directory or script. `TYPESAFE_ENV_FILE` chooses an explicit env file. If no key is found, a live request fails closed. `TYPESAFE_MODEL`, `TYPESAFE_BASE_URL`, and `--timeout-ms` are optional. Send the key only as bearer authentication; never put it or any other credential in review content. A local path does not grant JEV access to its contents. Include only necessary, non-sensitive excerpts, acceptance criteria, and verification evidence. The user's authorization covers non-secret review data, not authentication credentials. JEV review supplements and does not replace tests, type checks, or lint.
