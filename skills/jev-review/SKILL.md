# JEV review

Use this skill after a plan is generated or after an implementation checkpoint when an independent validity judgment will improve the next decision. Gather the relevant plan or diff, acceptance criteria, test evidence, and known constraints before composing a request. Keep the request focused on the decision that needs review.

Create a JSON request containing `model` (optional), `state` (context and acceptance criteria), and a non-empty `questions` object. The examples in [references/requests.md](references/requests.md) cover plan and checkpoint reviews. Submit it with:

Resolve the skill directory first, then run its script so the instructions remain portable when the skill is copied:

```sh
SKILL_DIR=/path/to/jev-review
node "$SKILL_DIR/scripts/jev-request.mjs" --request request.json --output review.json
```

The client validates the request JSON before sending. It uses `TYPESAFE_API_KEY` when explicitly exported and otherwise searches ancestor directories from the current directory and the skill script for `.env.local`, using its `TYPESAFE_API_KEY` by default. Set `TYPESAFE_ENV_FILE` to select an explicit env file. `TYPESAFE_MODEL`, `TYPESAFE_BASE_URL`, and `--timeout-ms` remain optional. A live request fails closed when no key is available. The client uses the existing TypeSafe JEV endpoint contract (`POST /v1/systemone`, bearer authentication, JSON body) and refuses to overwrite an output file.

Treat a successful HTTP response as transport success only. Inspect the preserved `rawResponse` and the actual JEV choices, probabilities, confidence, evidence, and limitations. An API error, timeout, malformed JSON, missing response, or non-positive judgment never counts as approval. Apply a bounded fix when the review identifies one, rerun the relevant checks, and submit a new request when the fix could change the judgment. Do not assume an automatic hook exists; invoke this workflow explicitly at the plan or checkpoint boundary.

Normal initial requests should use the single-distribution schema shown in [references/requests.md](references/requests.md): set `schemaVersion` to `jev-review-initial-distribution-v3` and ask one choice question. Its mutually exclusive choices are `valid_as_defined`, the six reason categories `requirements_mismatch`, `missing_prerequisites_info`, `incomplete_implementation_info`, `implementation_issue`, `scope_violation`, and `other`, plus `indeterminate`. Only `valid_as_defined` is a pass (`合格`); each reason category is a non-pass requiring a case-specific finding, affected location or requirement, observed evidence, and either a concrete proposed fix or exact additional evidence. A reason category does not encode severity; do not infer `valid_but_limited` or `not_valid` from it. `indeterminate` is a separate unresolved state, not a defect reason. Preserve the selected choice's confidence and complete probability distribution; expose the probability assigned to `valid_as_defined` as `passProbability`, the pass mass. If a reason category lacks required details, report `diagnosisStatus: "incomplete"` and recommend clarification. Unknown, missing, duplicated, or malformed answers fail closed.

Saved results using `jev-review-initial-distribution-v2` remain readable with their original choices (`evidence_insufficient`, `acceptance_gap`, `implementation_mismatch`, and `constraint_conflict`) and summary semantics. Do not use those v2 reason IDs in new initial requests.

Previously saved three-question results (`failure_reason` and `next_action`) and legacy one-question results remain readable with their original semantics. In the three-question format, only the main choice determines the verdict; diagnostic inconsistencies fail closed as recorded by that schema. Legacy custom non-empty criteria remain accepted; only exact `valid_as_defined` can pass. New local results store `reviewSchemaVersion`; dispatch parsing and clarification by that version while retaining old saved results. The existing generic follow-up behavior remains a non-standard CLI utility.

For the single-distribution schema, `decisionSummary` preserves the selected `choice`, `confidence`, the full `probabilities`, and finding/evidence/remedy details when returned. Do not derive a severity verdict from a reason category or use the category name itself as the case-specific finding. A complete reason diagnosis requires a non-empty case-specific finding, an affected location or requirement, observed evidence, and either a concrete fix or specific additional evidence. A selected reason with incomplete details stays non-pass with `diagnosisStatus: "incomplete"` and `followUpRecommended: true`. `indeterminate` is also incomplete. Do not use criterion fallback to fabricate a specific finding. The previously saved three-question schema retains its existing `failureReasonChoice`, `nextAction`, and diagnostic completeness semantics. The follow-up utility and clarification can explain or refine a diagnosis but cannot change the original verdict; only a new regular initial review after adding evidence or making a fix can pass.

For a new v3 initial request, every valid non-pass answer (`indeterminate` or any of the six reason categories) automatically triggers exactly one implementation-specific clarification. The client derives at least two mutually exclusive immediate next actions from the initial finding, affected requirement, evidence, proposed fix, and needed evidence. Its default choices separate changing the implementation under the current requirement, revising the requirement under the current implementation, and collecting evidence without changing either. Each choice repeats the case finding, affected location or requirement, and evidence (or explicitly says JEV omitted that detail), then bounds the one permitted immediate action and excludes the other actions. It sends those options to JEV as the choice criteria and asks JEV to select one, explain the evidence and next action, and state remaining uncertainty. Codex does not choose an option and does not ask the user to choose. An initial `valid_as_defined` result does not trigger clarification. Transport failures, invalid responses, unsupported formats, and unknown or missing choices keep the existing initial-error behavior and do not trigger clarification.

The automatic clarification must return the selected choice ID plus a case-specific finding, affected location or requirement, observed evidence or exact `neededEvidence`, concrete `nextAction` or `proposedFix`, and `remainingUncertainty` (explicitly `none` when resolved). Repeat the affected and evidence details in the clarification and tie them to the selected action. A choice-only or otherwise incomplete diagnosis keeps `selectedChoice` and `rawResponse`, but is stored as `resolution: "unresolved"`, `diagnosisStatus: "incomplete"`, with `unresolvedReasons`; it is not an `action_selected` result. The initial result is preserved unchanged, including its `decisionSummary` and choice probabilities. The separate `automaticClarification` result always has `effectiveVerdict: "requires_revalidation"`; it cannot promote or replace the initial non-pass. A response that is invalid, fails transport, selects an ID outside the offered choices, or omits required diagnosis details is saved as unresolved alongside the initial result. This is a one-time clarification; never chain another or ask the user to repair it. Make the suggested bounded fix or collect the requested evidence, then run a new normal initial JEV review.

Manual `--clarify INITIAL_RESULT --choices-file FILE --choice ID` remains available for explicit compatibility use, as does non-standard `--follow-up` with fixed reason IDs. These manual utilities are not part of the standard automatic path. The clarification CLI still requires at least two unique choices and a valid user-supplied `--choice`; clarification always requires revalidation.

Do not put API keys, credentials, or other secrets in the request context. The key in `.env.local` is used only for bearer authentication and is never sent as review content. A local file path alone does not give JEV access to its contents; include only the necessary, non-sensitive excerpts, diff summary, acceptance criteria, and verification evidence. For this workflow, the Codex user's request explicitly authorizes sending those non-authentication review data to JEV; do not pause for another approval solely for that content. Authentication credentials themselves are excluded from that authorization and must never be sent to JEV. JEV review supplements tests and must not be treated as a test replacement.
